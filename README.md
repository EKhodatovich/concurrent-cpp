# Конкурентная обработка на С/C++

**Задача:** написать консольное приложение, которое построит Merkle tree из библиотеки файлов `/data`.
При решении задачи используем хеш-функцию `crc32` из библиотеки zlib: https://zlib.net/manual.html
Подробнее про структуру данных: https://habr.com/ru/articles/873718/

**Алгоритм решения:**
1. читаем директорию `/data`, для чтения используем `readdir` или `std::filesystem::directory_iterator`;
2. сортируем имена файлов;
3. для каждого файла в директории считаем хеш `crc32()`;
4. попарно объединяем хеши (0-ый с 1-ым, 2-ой с 3-им, 4-ый с 5-ым и т.д.) функцией `crc32_combine()`,
сохраняя порядок сортировки из шага 2; если массив нечётной длины, последний элемент объединяется сам
с собой;
5. повторяем шаг 4 до тех пор, пока в массиве не останется 1 элемент, этот результирующий хеш -
результат работы программы, его выводим в `stdout`.

**Пример (псевдокод):**
```
ls -1 /data
a.txt
b.txt
c.txt
```
```
crc32(a.txt) => 77f85d95
crc32(b.txt) => 4c261fe1
crc32(c.txt) => ec4323f2
```
```
crc32_combine(77f85d95, 4c261fe1) => 93cd7de5
crc32_combine(ec4323f2, ec4323f2) => bdcdeefd
```
```
crc32_combine(93cd7de5, bdcdeefd) => c459a5b1
```

💡 У этой задачи может быть несколько решений, начни с простого неоптимизированного решения и
постепенно усложняй.

## С чего начать

В репозитории уже есть базовое окружение:

Начни с выполнения команды `make`. Далее можешь либо удалить `src/main.cpp` и начать выполнение

## Уровень сложности 1. Тривиальное однопоточное решение

Просто реализуй описанный алгоритм, без усложнений

## Уровень сложности 2. Fan-out / fan-in

Можно заметить, что шаги алгоритма 3, 4, 5 можно выполнять параллельно. Рассмотрим на примере шага 3:
1. пробегаем по массиву;
2. на каждый файл создаём отдельный поток через `pthread_create()`;
3. после завершения цикла делаем ещё один цикл, ожидаем завершения всех потоков через `pthread_join()`.

В результате выполнения мы должны увидеть серьёзный прирост производительности: задачи теперь
выполняются параллельно, а не последовательно.

## Уровень сложности 3. Thread pool

На предыдущем уровне есть 2 проблемы:
1. cоздание потоков - дорогая операция, короткоживвущие потоки создают оверхед по производительности;
2. кол-во потоков никак не ограничено - если потоков больше чем ядер процессора, это тоже создаёт
оверхед на переключение контекстов, потоки начинают мешать друг другу; в контейнеризованной среде
такая арзитектура многозадачности вызывает троттлинг CPU.

Что такое троттлинг CPU: https://habr.com/ru/companies/flant/articles/489668/

Решим проблему с помощью пула потоков:
1. создадим 2 очереди: очередь входящих задач и очередь результатов выполнения;
2. создадим массив долгоживущих потоковб каждый поток крутит бесконечный цикл:
- взять задачу из входной очереди;
- обработать задачу (в нашем случае, посчитать хеш);
- положить результат в выходную очередь;
3. вместо fan-out будем записывать задачи во входную очередь, вместо fan-in будем разгребать очередь
результатов выполнения.

⚠️ Не забдь защититься от гонки при работе с очередями.

💡 Тредпул может обрабатывать задачи разного типа, в нашем упражнении есть как минимум 2 типа задач:
- посчитать `crc32` от файла;
- посчитать `crc32_combine` от двух хеш-сумм.

💡 Подробнее про тердпул: https://habr.com/ru/articles/656515/

## Уровень сложности 3. Prefork

Вместо пула потоков можно использовать пул заранее созданных процессов, такая модель называется prefork.
Для создания процесса используется системный вызов `fork()`.

Ключевые отличия prefork от thread pool:
- между процессами сложнее передавать задачи, чем между потоками - придётся поиграть с пайпами/сокетами
и отправкой сообщений;
- prefork в целом менее эффективен, чем тредпул, но чуть более безопасен: при панике в обрабтке задач
умрёт только один воркер-процесс, не приложение целиком.

💡 Я рекомендую начать с тредпула, и играть с префорком если это будет интересно.

## Уровень сложности 4. Неблокирующий ввод-вывод

Неблокирующий ввод-вывод позволяет эффективнее расходовать CPU и избегать блокировок при чтении/записи
файлов.

Для неблокирующего решения нужно использовать асинхронное API операционной системы, в Linux есть 3
варианта (от самого старого и медленного к самому современному и быстрому):
- `select` - https://man7.org/linux/man-pages/man2/select.2.html
- `poll` - https://man7.org/linux/man-pages/man2/poll.2.html
- `epoll` - https://man7.org/linux/man-pages/man7/epoll.7.html

Подробнее про них - тут https://habr.com/ru/companies/infopulse/articles/415259/

Решение проще сделать с помощью библиотеки libevent, у неё более высокоуровневое API и больше примеров
по сравнению с системными вызовами: https://github.com/libevent/libevent

План неблокирующего решения:
- создаём структуру для цикла обработки событий, в ней будут храниться дескрипторы для наблюдения и
коллбеки на события: `event_base_new()`;
- все файлы открываем с флагом `O_NONBLOCK`;
- для каждого файла создаём вотчер события "файл готов на чтение" `event_new()`;
- в коллбеке на событие "файл готов на чтение" читаем файл и считаем `crc32()` до тех пор, пока операция
чтения не вернёт `EAGAIN`, при обнаружении `EAGAIN` - выходим (коллбек будет вызван снова при следующем
событии), при обнаружении `EOF` убираем событие с ивентлупа;
- когда коллбеки установлены, запускаем ивентлуп; тебе подойдёт простой `event_base_dispatch()`, но в
целях обучения я советую писать так, чтобы лучше понять, что обработка событий происходит в цикле:
```c++
while (true) {
	event_base_loop(base, EVLOOP_ONCE);
}
```

Пример использования библиотеки: https://github.com/libevent/libevent/blob/master/sample/event-read-fifo.c

Результаты блокирующего и неблокирующего решений должны совпасть, но на достаточно большом датасете
неблокирующее решение должно работать быстрее.
